The Control Plane, Deeply

You have seen the loop close the gap — desired on one side, actual on the other, a controller squeezing the difference to zero. This is the same machine, opened up: how the ledger agrees with itself, how writes race without locks, how one watch stream replaces a million polls, and why a component you kill -9 at 3am owes nobody an apology.

01 the shape

One door, one ledger, many loops

Strip away the deployment diagrams and Kubernetes has one shape: a hub with spokes. At the hub sits the API server, a stateless HTTP server that exposes every object in the cluster — Pods (the unit of one or more running containers), Nodes (the machines they run on), and everything else — as REST resources. Behind it sits etcd, a replicated key-value store that holds the cluster's entire state.

The scheduler, the controller manager, the kubelet on every node, kubectl, your CI pipeline — each is an authenticated API client, no different in kind from a shell script calling curl. Every other component in the system is a client of that one API, and nothing more. Watch for the edges that never appear — and for what keeps working when components start dying.

By design, etcd accepts connections from exactly one client: the API server. That single door is where authentication, authorization, and audit logging happen — once, identically, whether the caller is a kubelet or an intern's laptop. The failure mode this kills is the one most systems accrete: a dozen components holding their own database credentials, each enforcing its own idea of validation, none producing a coherent audit trail.

The control-plane spokes hold no durable state of their own: a controller's in-memory cache is built by listing objects from the API and then watching for changes — no local database to corrupt, no snapshot to restore. If losing a control-plane component's disk loses information, the design is broken. That statelessness is what makes the control plane crash-only: Kubernetes does not lean on graceful shutdown, because a shutdown protocol only protects you when processes exit politely, and the outage you care about is the one where they don't. The crash path and the clean-exit path are the same path, so the recovery code runs on every restart instead of rotting until the incident that needed it.

The dark hub divides control plane — the components that decide — from data plane, the nodes where your containers execute. Containers survive because kubelets keep supervising them locally and traffic keeps flowing along routes already programmed into each node; what stops is change — no new rollouts, no rescheduling off a dead node, no scaling. You lose the ability to change things, not the things themselves. Debugging means querying one API: desired state and reported actual state sit side by side, inspectable with kubectl get, because there is nowhere else for shared state to live; and because the API is the only contract components share, each is independently replaceable — swap the stock scheduler for your own.

the usual wrong model

Newcomers picture an RPC pipeline: kubectl calls the API server, which calls the scheduler, which calls the kubelet, each command flowing forward until the container starts.

what actually happens

No component calls another. Each writes records into the shared store through the API server and independently watches for records that concern it — a Pod starts because several watchers each reacted to state, not because anyone issued a command.

the pattern to steal

Put one gateway in front of one authoritative store, and make every other component a stateless, crash-restartable client that rebuilds its world from that store on startup. Components then coordinate by writing records that others observe — coordination becomes data, which makes it auditable, replayable, and inspectable in ways an RPC chain never is.

02 the source of truth

etcd: one history, in order

Everything the control plane knows — every Pod, every piece of configuration — lives in etcd, a replicated key-value store. Keep that store on one machine and the machine is a single point of failure for the entire cluster. Replicate it naively — two copies, both accepting writes — and a network partition produces split-brain: two divergent histories that no merge can honestly reconcile. The problem consensus solves is not durability; it is agreement — after any failure, exactly one history survives.

Watch what a write must earn to count as committed, how the cluster outlives its leader yet freezes when split evenly, and why every key grows a stack of versions under one climbing counter instead of overwriting. That stack looks wasteful; the entire control plane is built on it.

The protocol is Raft, built around one replicated, append-only log: every write flows through the leader and commits only once a majority — a quorum — has persisted it. Followers wait out an election timeout of roughly a second before electing a replacement under a fresh term — a monotonically increasing epoch number. What stops a revived old leader is quorum overlap: any majority it would need to commit overlaps the majority that elected its successor, those members reject its stale term, and it steps down on seeing the higher one.

Quorum arithmetic decides sizing: a majority of 3 is 2, of 5 is 3, of 4 also 3 — a fourth member buys nothing but replication traffic and another machine that can fail. Production control planes run 3 or 5, never 4; when quorum is lost entirely, etcd refuses writes rather than guess — unavailable beats divergent. The version stacks are MVCC: every write, to any key, increments one global revision — a logical clock, no wall clocks, no clock-skew arguments — surfaced to clients as resourceVersion, opaque by contract: something you hand back, never a number you parse or compare.

Keeping every version forever would grow etcd without bound, so it compacts, and a watcher that fell too far behind gets HTTP 410 Gone: it must re-read current state and watch from there. Resynchronization is a designed-for event, not an emergency. Only the API server talks to etcd — partly policy (section 03), partly load: a large cluster runs tens of thousands of watchers, and a store paying a round of consensus per write cannot also serve them all, so the API server's watch cache serves nearly all watches and much of the read traffic. Consensus is paid once per write and amortized across every reader.

the usual wrong model

etcd is where Kubernetes keeps its data — a database that cluster components query and update the way an application talks to Postgres.

what actually happens

Only the API server ever touches etcd, and most reads never reach it at all. What etcd actually provides is ordering: one agreed-upon history of changes with positions you can subscribe from — the key-value storage is almost incidental.

the pattern to steal

Pay for consensus exactly once, at a single replicated log that stamps every change with a global monotonic version, and make everything else a disposable subscriber that resumes from a version — or re-reads and re-subscribes when it falls too far behind. The product is order, not storage: a change feed with exact positions turns caching, replication, and crash recovery into the same operation.

03 the request pipeline

A pipeline, not a brain

Strip away the mythology and the Kubernetes API server (kube-apiserver) is a REST server in front of a key-value store. It does not schedule pods onto nodes, does not restart failed containers, does not compare desired state to actual state. The API server is a validating, versioning storage gateway — every piece of cluster intelligence lives in its clients.

Then what earns a write the right to land in etcd? Follow one request — kubectl apply (the CLI submitting a manifest) creating a Deployment — and watch who may change the object, who may only refuse it, and whether anything can still touch it after a check has passed.

Authentication — client TLS certificates, bearer tokens, or OIDC — produces a username plus groups and approves no action, so you can swap identity providers without touching a single access rule. RBAC grants verbs on resources — get, create, patch — but has no opinion about the contents of the object: a cheap identity-level check rejects illegitimate traffic before the server spends effort on the payload. Schema defaults were stamped in at decode, and mutating webhooks are external HTTP services you register. The ordering is the security property: validation and policy always see the final object, so no mutation can slip in after a check has passed.

A group/version like apps/v1 is a wire contract, not a storage format: the server converts every request through a hub version — each of n served versions needs one converter, not n² pairwise — and persists at exactly one storage version, which lets a cluster upgrade its API without a flag-day migration. The /status side door is a permission boundary: users write spec — intent — controllers write status — observation — and RBAC can grant each side only its half. Without the split, a user could forge "this pod is healthy," and no rule could let a controller report observations without also letting it rewrite intent.

Because the pipeline contains no per-type logic, a new type is configuration, not code: post a CustomResourceDefinition (CRD) — a schema plus a group/version/kind name — and the API server starts serving the new resource, RBAC and watch streams included. A CRD buys your custom type the entire machine for the price of a schema — the mechanism behind the operator ecosystem. Every durable fact lives in etcd, so replicas run all active, no leader election. Components that make decisions must elect a leader to avoid dueling actors; a gateway that decides nothing has nothing to duel over.

the usual wrong model

The API server is the brain of the cluster — it decides where pods run, notices failures, and drives the system toward the desired state.

what actually happens

It decides nothing about the cluster. It authenticates, authorizes, mutates, validates, versions, and stores; scheduling and reconciling are done by separate components that are ordinary clients of the same API you use.

in practicerbac.yaml
# Who may do what — enforced at the one door, identically for every client.
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: deployer
  namespace: shop
rules:
- apiGroups: ["apps"]
  resources: ["deployments"]
  verbs: ["get", "list", "watch", "update", "patch"]   # no delete, no create
---

kind: RoleBinding
metadata:
  name: ci-deploys
  namespace: shop
subjects:
- kind: ServiceAccount
  name: ci-bot
  namespace: shop

  kind: Role
  name: deployer
  apiGroup: rbac.authorization.k8s.io

A request from ci-bot outside these verbs and resources dies at the RBAC gate with 403 — before admission, before validation, before anything.

the pattern to steal

Keep the gateway dumb: put one generic, stateless authenticate-validate-version-store pipeline in front of your database and push all domain intelligence into clients of its public API. The gateway then scales by replication with no election, and new object types cost a schema instead of a code change.

04 optimistic concurrency

No locks, only retries

When dozens of controllers write to the same objects, the reflex is to serialize them — take a lock, mutate, release. But a distributed lock is a liability with a failure mode attached. The holder crashes mid-update and the lock stays held forever, so you add a TTL; now a holder stalled in a long GC pause has its lock expire while it still believes it owns it, so you add fencing tokens. Each patch to pessimistic locking adds a new machine that can itself fail.

Kubernetes opts out of the entire ladder: no write to an object ever waits on a lock. So what referees dozens of concurrent writers — and what does one that dies mid-flight leave behind? Watch the version number stamped on every copy.

The referee is metadata.resourceVersion: an opaque string — underneath, the etcd MVCC revision from section 02 — naming the write that produced your copy. A PUT carrying a stale version is rejected with 409 Conflict: the server never blocks a writer; it refuses stale ones. This is compare-and-swap, lifted from a CPU instruction to an HTTP API. Client-go ships the re-GET-and-retry loop (retry.RetryOnConflict) because a 409 is not an error path but the ordinary cost of concurrency. A crashed writer leaves nothing to expire, fence, or clean up — the fact section 01's crash-only design rests on.

One counter is not enough: resourceVersion changes on every write — a status update, another controller's touch — so it cannot answer the question you have after kubectl apply: has the controller acted on my change yet? Hence the second counter: metadata.generation, incremented only when the spec changes, and status.observedGeneration, the generation the controller most recently processed. If the second lags the first, every status field describes your previous intent — a Deployment can report healthy moments after you pushed a broken image, and comparing these two numbers is how you avoid believing it.

The version check cannot referee field-level ownership, because the danger there is not staleness: a deploy pipeline re-applying its full manifest holds a fresh resourceVersion, and its write legally resets the replicas the autoscaler set — the classic read-modify-write clobber. Server-side apply instead records in metadata.managedFields which manager set which field; each writer submits only the fields it cares about, and the server merges, conflicting only when two managers claim the same field. The unit of ownership drops from the object to the field, so co-ownership stops being a race. Even leader election reintroduces no lock: a single active actor is chosen by CAS on a Lease object, which section 10 takes apart.

the usual wrong model

A 409 Conflict means something went wrong — two components writing to the same object at once is a race that Kubernetes must be preventing with a lock somewhere.

what actually happens

There is no lock anywhere; concurrent writers losing races is the designed steady state. Well-behaved clients wrap writes in a re-GET-and-retry loop, and a background rate of 409s on a busy cluster is contention being resolved, not malfunction.

in practicethree answers to the same race
# A write that carries a resourceVersion meets the check head-on.
# Replace from a stale copy and the API answers:
kubectl replace -f web.yaml
#   Error from server (Conflict): Operation cannot be fulfilled on
#   deployments.apps "web": the object has been modified; please
#   apply your changes to the latest version and try again   # HTTP 409

# The declarative path sidesteps it: apply computes a three-way merge
# (your file, the live object, the last-applied record) and sends a
# PATCH with no resourceVersion — no version check to trip:
kubectl apply -f web.yaml

# Server-side apply: field-level ownership. Two managers writing the
# same field get an explicit conflict instead of a silent clobber:
kubectl apply --server-side --field-manager=ci -f web.yaml
#   error: Apply failed with 1 conflict: conflict with
#   "kubectl-client-side-apply" using apps/v1: .spec.replicas
#   (yield the field, or take it with --force-conflicts)

Controllers hit that 409 constantly and wrap writes in a re-GET-and-retry loop. kubectl apply avoids the race by patching instead; server-side apply turns it into an explicit field-ownership conflict. Same race, three answers.

the pattern to steal

Version every record and make every write conditional on the version the writer read; reject stale writes with a retryable error instead of making writers wait. Any number of writers can then coordinate without a lock service, and a writer that crashes mid-operation leaves nothing to expire, fence, or clean up.

05 the read path

Watch, do not poll

Start with the arithmetic. A production cluster holds tens of thousands of objects — Pods, Services, ConfigMaps, EndpointSlices — and dozens of control loops each need to notice when any of them changes. Poll once a second from every loop and that is hundreds of thousands of object reads per second pressed against a store that replicates through a Raft quorum — and polling has no good frequency: poll fast and you melt etcd, poll slow and every reaction waits out the interval.

Polling charges you for reads whether or not anything changed; a watch makes cost proportional to the rate of change. Kubernetes buys that trade with a two-step contract, list+watch: watch the version stamp on the snapshot, and what it lets the client do when the stream breaks.

The snapshot's stamp, resourceVersion, is the etcd revision counter — a cluster-wide logical clock. A consistent snapshot plus an ordered, gap-free stream of deltas is a replication protocol: the client maintains a perfect local replica for the cost of one open HTTP connection. Drop either guarantee and the replica silently corrupts. The 410 Gone arrives when the server has already compacted the requested history away; relists are the expensive path, so the server periodically sends bookmark events — an otherwise-empty object carrying only the current resourceVersion — keeping even a watcher on a quiet resource from falling far behind.

client-go packages this loop: its reflector feeds a DeltaFIFO keyed by object — all pending changes to one object accumulate under a single key and pop together — and the informer's cache is indexed by namespace, by name, by any index you register. Informers are shared: kube-controller-manager hosts dozens of loops, yet a shared informer opens one watch stream per resource type per process. The API server is consulted on writes and once per type for the stream — never per decision. Without sharing, connections would scale as controllers times types; with it, a controller's read costs a map lookup.

Handlers only extract a namespace/name key and enqueue it — nothing else. Each subscriber's handlers run in order on one dispatch goroutine, so a handler that blocks on I/O stalls every later event bound for that subscriber while the undelivered backlog piles up in memory. Ten rapid updates to one object collapse into one queued key. And the resync fires on a configurable interval — minutes or hours, not seconds — because edge-triggered systems die by dropped edges: a handler bug, a crash between dequeue and action, a delta mishandled once. Re-presenting the full cached state on a clock means a missed event costs latency, never correctness.

the usual wrong model

Controllers query the API server whenever they need an object's current state, so every reconciliation decision costs a round trip to the control plane.

what actually happens

Controllers read from a local in-memory cache kept current by one shared watch stream per resource type. The API server sits on the write path and the stream path — never on the per-decision read path.

the pattern to steal

When many consumers must react to changes in shared state, do not let them poll the store. Hand each one a consistent snapshot stamped with a version, then an ordered, gap-free stream of deltas from that version: each consumer maintains a local replica and serves its own reads, so the source of truth pays one stream per consumer instead of one query per decision.

06 the reconcile loop

Levels, not edges

There are two ways to make a system respond to change. An edge-triggered system reacts to each change notification as it arrives — the notification is the work; a level-triggered system compares the full desired state against the full actual state and corrects the difference. The distinction sounds academic until a process crashes in the gap between receiving an event and acting on it. An edge-triggered system that misses one edge drifts permanently; a level-triggered system converges from any starting state. The lost event never gets redelivered; the next comparison happens regardless.

Kubernetes controllers are level-triggered: watch events still arrive, but they are demoted to hints about when to look, never inputs to what to do. In the figure, watch what reaches the worker — and what never does.

A reconcile function receives one argument: a key, a namespace/name string such as payments/api, not the event that woke it, not a diff. Because the function cannot know what changed, it is forced to re-observe everything: desired state from the informer cache (the local, watch-maintained copy of the API server's data) and actual state. Miss an event and you lose freshness until the next hint or periodic resync; you never lose correctness.

The workqueue's collapse is only safe because the queue item carries no payload: reconcile re-reads the entire current state, so under an update storm work stays bounded by the number of objects, not the number of events. The same key never goes to two workers at once, so two reconciles of one object cannot race into creating duplicate children. And backoff is per-key, starting at milliseconds and capping near the scale of minutes, so one persistently failing object backs off alone, without hammering the API server or starving healthy keys.

Idempotency is not a virtue here; it is a load-bearing requirement. Any reconcile may run twice (a resync, a duplicate hint, a crash after acting but before the key was marked done), so creating a child that already exists must degrade to a no-op, treating 409 AlreadyExists as success, and deleting one already gone must swallow the 404. A controller never trusts its own writes: the write may have failed, been mutated by an admission webhook, or been reverted seconds later; the next loop observes reality again. A crash mid-reconcile loses no progress, because no progress is stored — only state is. The system refuses to depend on exactly-once event delivery (a guarantee distributed systems cannot cheaply give) and pays in redundant reads served from a local cache; Kubernetes buys correctness with the cheaper currency.

the usual wrong model

Controllers process the event stream — each watch event describes a change, the controller applies that change, and so the event log is effectively the source of truth.

what actually happens

Events never reach the reconcile function; only an object's key does. The controller re-reads full desired and actual state on every pass, so a lost or duplicated event costs a little latency, never correctness.

the pattern to steal

Never let correctness depend on delivering every event: store desired state durably, make workers pure functions of a key that re-observe full state and converge, and treat notifications only as cache-invalidation hints that say "look now." You trade cheap redundant reads for immunity to lost messages, duplicate delivery, and mid-action crashes.

07 the controller stack

Controllers compose

You run an application by creating a Deployment: an object holding a pod template, a replica count, and an update strategy. Pods must appear, roll over to a new image, and vanish when you delete — so the natural picture is one orchestrator that understands the whole plan, from your intent down to individual containers. The Deployment controller never creates a pod.

As the figure runs, watch how far each controller reaches — what it creates, and what it never touches — and notice that no loop ever calls or messages another. Then hold one question: midway through a rolling update, where does the rollout's progress live, and what happens if its controller dies right then?

A ReplicaSet's entire specification amounts to "keep N pods matching this template alive"; its controller counts the pods it owns that match its label selector — a rolling update, a revision, a rollback: that vocabulary does not exist at its layer. The opposed counters you watched are bounded by maxSurge, capping total pods above the desired count, and maxUnavailable, bounding available pods below it. The replica counts of the two ReplicaSets are the entire state of the rollout. A workflow engine that dies mid-sequence leaves you asking whether step four executed; kill this controller mid-update and its replacement reads two integers and resumes, because there are no steps — only a gap between two numbers.

Rollback is the same arithmetic: a bounded number of old ReplicaSets are kept at zero replicas as revision history, and restoring a template scales one back up through the identical code path as rollout — exactly as well-tested as the thing it undoes. Deletion composes through data: each child names its parent in metadata.ownerReferences, and the garbage collector — one more controller, maintaining a graph of who owns whom — deletes anything whose owner no longer exists. A parent that must clean up its own descendants can crash halfway and leak the rest; here the deletion intent lives in the data, where any later pass will find it.

kube-controller-manager hosts dozens of these loops in one binary; each maintains one invariant it can state in a sentence, and they share informer caches but no logic and no private channels — a bug in the Job loop can mangle Jobs while rollouts keep working. The seams are public: an operator is a custom controller encoding operational knowledge, riding the same watches and conflict-checked writes — and the control plane cannot tell your controller from its own.

the usual wrong model

The Deployment controller is an end-to-end orchestrator: it creates pods, watches them come up, and executes a scripted sequence of rollout steps.

what actually happens

It only writes ReplicaSet objects — pods are two layers away — and no component holds the rollout as a plan. The rollout's only state is the replica counts of two ReplicaSets, which is why a controller crash mid-update loses nothing.

in practicedeployment.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web
  namespace: shop
spec:
  replicas: 3                     # desired state — remove once an HPA owns scaling (last section)
  revisionHistoryLimit: 5          # old ReplicaSets kept around for rollback
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1                 # one extra pod may exist mid-rollout
      maxUnavailable: 0           # never dip below 3 — real only once a readinessProbe gates "ready"
  selector:
    matchLabels: { app: web }      # which pods this deployment owns
  template:
    metadata:
      labels: { app: web }         # must match the selector above
    spec:
      containers:
      - name: web
        image: ghcr.io/acme/web:1.7.2   # pin versions — :latest defeats rollback
        ports:
        - containerPort: 8080

Change image and the Deployment controller cuts a new ReplicaSet; kubectl rollout undo points back at the old one, which was kept for exactly this.

the pattern to steal

Decompose orchestration into a stack of small reconcilers, each owning exactly one parent-child relationship and communicating only through shared declarative state, never through calls to each other. Cross-cutting concerns like cleanup become one more reconciler over the same state, and because the seams are public data, third parties can add layers you never anticipated.

08 placement is a write

The scheduler: filter, score, bind

The scheduler sounds like it should be the most privileged component in the system: it decides which node — which worker machine — runs each pod. Yet it has no privileged interface at all. It is one more watch client, queueing every pod whose spec.nodeName is empty. It holds no lock on the cluster and no channel to the nodes; its entire authority is RBAC permission to set one field. Stop it and bind a pod by hand — POST the same request yourself — and the cluster cannot tell the difference.

So how does a component that can touch nothing but one field place every pod in the cluster? Watch where the scheduler's one arrow ends — and what keeps running when the scheduler dies.

Filter checks CPU and memory against the pod's declared requests, not live usage, so placement does not flap with load; a failed check is a hard constraint, no partial credit. Each score plugin returns a number per node — roughly zero to one hundred — multiplied by the plugin's weight and summed. Keeping filter and score separate keeps “cannot” out of the cost function: a single blended fitness score would let enough preference points outvote a hard constraint, and a pod would land somewhere it cannot run.

The bind is a POST of a Binding to the pod's binding subresource, setting spec.nodeName. Recording the decision instead of executing it means the record outlives the decider: if the scheduler crashes a millisecond after the write commits, nothing is lost and no handshake was left half-open. A scheduler that pushed launch commands over connections to nodes would have to answer what happens when a connection drops mid-command — Kubernetes never has to ask. Its only state is the ledger, so there is no journal to replay: a dead scheduler costs you placement latency, nothing else.

When filtering leaves zero nodes, preemption weighs priority, assigned through a PriorityClass: victims get their graceful shutdown, and the choice recorded in status.nominatedNodeName is a hint, not a reservation — the re-run may choose differently. Without preemption, a cluster full of batch work would lock out a critical pod forever; priority means nothing if arrival order always wins. Filter and score are plugin points in the scheduling framework, alongside pre-filter, reserve, permit, and pre-bind; one binary can run several profiles, selected per pod with spec.schedulerName. Because binding is an ordinary authenticated write, a custom scheduler is any program that watches for unbound pods and POSTs bindings — a toy one fits in a couple hundred lines.

the usual wrong model

The scheduler is the engine of the cluster: it starts containers on nodes, so if it dies, workloads die with it or at least cannot restart.

what actually happens

Its only output is writing spec.nodeName on pending pods; each kubelet launches pods it discovers through its own watch. A dead scheduler leaves running pods untouched — new pods queue as Pending until it returns.

in practicepod spec — placement inputs
    spec:
      containers:
      - name: web
        image: ghcr.io/acme/web:1.7.2
        resources:
          requests:                # what the SCHEDULER uses to place the pod
            cpu: 250m
            memory: 256Mi
          limits:                  # what the KUBELET enforces at runtime
            memory: 512Mi          # over this → OOMKilled. a cpu limit (unset here) throttles instead
      tolerations:                 # permission to land on the node pool reserved for web
      - key: dedicated
        operator: Equal
        value: web
        effect: NoSchedule
      topologySpreadConstraints:   # spread replicas across failure domains
      - maxSkew: 1
        topologyKey: topology.kubernetes.io/zone
        whenUnsatisfiable: ScheduleAnyway
        labelSelector:
          matchLabels: { app: web }

requests are a promise the scheduler plans around; limits are a fence the kubelet enforces. Omit both and the scheduler places your pod blind — omit only requests and they quietly default to the limits.

the pattern to steal

Separate deciding from acting: have the decider publish its choice as a durable record in the shared store, and let executors discover and act on it through their own subscriptions. The decision then survives the decider's crash, the decider stays out of the data path, and any process with write access can replace or supplement it.

09 the loop at the edge

The reconciler at the edge

Every loop so far has run inside the control plane. The kubelet — one process per machine — ships that same shape to the edge: its desired state is the pod specs bound to its node, watched with a field selector on spec.nodeName; its actual state, the containers running on the machine beneath it. The kubelet is a reconciler whose actuator is a container runtime instead of a REST API.

But the edge has a wake-up problem the control plane never had: containers die below Kubernetes, in the kernel and the runtime, and no API event announces it. Scheduling was a field write; nothing pushes commands to the node. Watch the arrows: what flows down, what flows up, and how a death the API never saw gets noticed.

The kubelet speaks the Container Runtime Interface (CRI), a gRPC API implemented by a runtime such as containerd or CRI-O. It exists because the coupling it replaced was a failure mode — the kubelet once drove Docker through version-fragile glue code. Kubernetes runs no containers anywhere; it is management all the way down. The probe verdicts differ because restarting an overloaded server destroys its warm state and amplifies the overload; taking it out of rotation lets it recover. Restart the deadlocked, drain the busy — the exponential backoff between attempts is the CrashLoopBackOff you have seen.

The PLEG — pod lifecycle event generator — closes the gap: historically it relisted every container's state from the runtime roughly once a second; newer kubelets can subscribe to evented streams from the CRI, with a slower relist as backstop. Watch for speed, rescan for truth. Heartbeats get a tiny object — a Lease renewed roughly every ten seconds — because rewriting the large Node status every few seconds across a few thousand nodes is an etcd write storm; a renewal is a few hundred bytes. The node controller, a loop inside kube-controller-manager, watches for silence at two timescales, because the two mistakes carry different prices: flagging a node through a network blip is cheap, but mass-evicting healthy pods is a self-inflicted outage. Nothing detected a failure; a timestamp went stale.

The final beat resolves a circularity: the API server runs as a pod, but pods normally come from the API server. Static pods break it — the kubelet runs any pod spec it finds in a local manifest directory and reports read-only mirror pods upward; kubeadm writes the etcd and kube-apiserver manifests to disk. The system hosts itself: the loop at the edge is the loop that boots the center.

the usual wrong model

The control plane operates the nodes: the scheduler or a controller connects to each machine and instructs it to start and stop containers.

what actually happens

Nothing calls into a node. Scheduling is one field written to a pod record; the kubelet independently watches for pods bound to its node and drives the container runtime itself, so a node keeps its workloads converged even while the control plane is down.

in practiceprobes — feeding the actual state
      containers:
      - name: web
        image: ghcr.io/acme/web:1.7.2
        startupProbe:              # gates the other probes until boot completes
          httpGet: { path: /healthz, port: 8080 }
          failureThreshold: 30     # 30 × 2s — up to a minute of grace at boot
          periodSeconds: 2
        readinessProbe:            # fail → removed from Service endpoints
          httpGet: { path: /ready, port: 8080 }
          periodSeconds: 5
          timeoutSeconds: 3        # the 1s default times out on any GC pause
        livenessProbe:             # fail → container restarted, with backoff
          httpGet: { path: /healthz, port: 8080 }
          periodSeconds: 10
          timeoutSeconds: 3
          failureThreshold: 3      # three misses before the kubelet restarts it

Readiness gates traffic; liveness restarts. Point liveness at deadlock detection only — never at a dependency, or a flaky database restart-storms your whole fleet.

the pattern to steal

Ship the same reconciliation loop to your edge agents instead of commanding them: each agent watches the central store for its slice of desired state, actuates locally, and reports observations back through the same API — so the edge keeps converging even when the center is unreachable. Prove agent liveness with a small dedicated heartbeat record, separate from bulk status, so health signaling stays affordable at scale.

10 high availability

One driver at a time

Run the control plane on one machine and that machine is your cluster's single point of failure. The fix differs per component: stateless API servers replicate active-active, etcd commits on quorum — but replicate the scheduler or the controller-manager active-active and you have run the same loops twice against the same state. Two live controller-managers would each observe a ReplicaSet short one pod and each create one.

So these components run active-passive: several replicas, exactly one doing work — which raises the question of who decides, and there is no coordination service to ask. As the figure plays, watch what leadership physically is, what a takeover costs while no one leads, and — the sharpest test — what happens when a leader that merely paused wakes up convinced it still leads.

The object being fought over is a Lease: an ordinary API object in the coordination.k8s.io group whose interesting fields are holderIdentity, renewTime, and leaseDurationSeconds. Acquiring it is a write like any other: read the Lease, check it is empty or expired, and write your identity into it — against the resourceVersion you read, the same optimistic-concurrency check that guards every other write. Election is not a new mechanism — it is one more compare-and-swap, serialized by the same Raft log as everything else. The failure mode avoided is a second consensus system to deploy, secure, upgrade, and page on alongside etcd.

The timings the figure compresses: the leader renews renewTime every couple of seconds, standbys re-read it on the same cadence, and after roughly fifteen seconds the lease is expired in every standby's eyes. The leaderless window costs nothing, because the loops are level-triggered: the new leader lists current state and finds every piece of pending work already in it. Nothing sat queued in the dead leader's memory that a fresh list cannot reconstruct.

One caveat the coda only gestures at: a leader that pauses — a long GC pause, a frozen VM — rather than dies can wake after expiry still believing it leads, and act for a moment while its successor is already working. Lock-based systems need fencing tokens to survive this; Kubernetes absorbs it instead. Updates built from the stale leader's pre-pause view carry old resourceVersions and land as 409, and any duplicate it manages to create is surplus for the next idempotent reconcile to delete — the Lease exists to prevent duplicate work; safety lives in the CAS on each individual write. Recovery is not a separate code path that runs rarely and rots; it is the reconcile loop, the code path that runs every second of every ordinary day.

the usual wrong model

Newcomers assume Kubernetes runs a dedicated election or coordination service (something like ZooKeeper), and that holding the leader lock is what makes it safe when two processes think they lead.

what actually happens

There is no election service: leadership is an ordinary Lease object won by a CAS write through the API server, and safety comes from every write being CAS-guarded — a stale leader's updates from its outdated view die as 409s, whatever the lease says.

the pattern to steal

If every write in your system already goes through compare-and-swap against a versioned store, leader election needs no lock service: model leadership as a plain record with a holder identity and an expiry, acquired and renewed with the same CAS as your data. Keep correctness in the per-write CAS rather than in the lease, so a paused-then-resumed stale leader produces conflicts and cleanable duplicates, not corruption.

11 the data plane

The packet that never meets the Service

The walkthrough gave every Service a stable address: the pods behind web.shop churn while 10.96.0.12 holds still. The natural mental model is that something answers at that address — a load-balancer process accepting connections and forwarding them. Go looking for it and there is nothing to find. No process anywhere listens on a ClusterIP. No pod holds the address; it exists only as a row in the ledger and as rewrite rules on every node.

The naive design — a real box in the middle — costs what middleboxes always cost: an extra hop on every connection, a throughput ceiling, one more failure that takes all traffic with it. Watch the packet instead: where its destination changes, and what never touches it.

The rewrite happens in the client node's kernel. kube-proxy runs on every node, but despite the name it proxies nothing: it is a controller that watches Services and EndpointSlices and compiles them into kernel rules — iptables chains or IPVS tables — that DNAT a packet's destination from the ClusterIP to a real pod IP as it leaves. eBPF dataplanes like Cilium can drop kube-proxy entirely and install the same logic as kernel programs. Either way, no process sits in the data path. The failure mode this kills is the middlebox: a hop that must scale with traffic and takes every flow down with it when it dies.

The set of legal rewrite targets is itself an object. The EndpointSlice controller watches pods and maintains, per Service, the list of backend IPs — each entry a target only while its pod passes its readiness probe, which is how the kubelet's probe verdicts reach routing: a pod failing readiness drops out of every node's rules without being restarted. When a backend dies, the update is pure ledger: the kubelet reports the pod gone, the EndpointSlice controller trims the list, and every node's kube-proxy sees the watch event and reprograms. No node tells another node anything; a thousand rule tables converge because all watch the same record.

Naming runs on the same machinery. CoreDNS resolves web.shop.svc to the ClusterIP — no privileged infrastructure, just a pod running a controller that watches Services and answers from cache. Ingress repeats this one layer up: an Ingress object is routing data in the ledger, and an ingress controller — an ordinary pod running nginx or envoy — watches those objects and rewrites its own configuration. Watch-and-reconcile does not care whether it programs a kernel table, a DNS zone, or a reverse proxy.

the usual wrong model

A Service is a load balancer — a process that receives your connection at the ClusterIP and forwards it to a pod, the way an nginx or HAProxy box would.

what actually happens

A Service is a row of data. Every node independently compiles that row into local kernel rewrite rules, so the packet is redirected to a pod IP in flight; nothing ever receives traffic at the ClusterIP itself.

in practiceingress.yaml — L7, same pattern
# Inside the cluster, DNS + the VIP already work with zero config:
#   web.shop.svc.cluster.local → 10.96.0.12
#   (a virtual IP: no pod answers for it — every node's kernel rewrites it)

# For traffic from OUTSIDE, describe the route — as data:
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: web
  namespace: shop
  annotations:
    cert-manager.io/cluster-issuer: letsencrypt   # TLS via yet another controller
spec:
  ingressClassName: nginx          # which watching controller acts on this
  rules:
  - host: shop.example.com
    http:
      paths:
      - path: /
        pathType: Prefix
        backend:
          service:
            name: web              # → the Service → the EndpointSlice → pods
            port:
              number: 80
  tls:
  - hosts: [shop.example.com]
    secretName: shop-tls           # cert-manager's ACME flow fills this Secret

An Ingress does nothing by itself — it is a row in the ledger. The ingress controller watches it and reprograms itself. cert-manager spots the cluster-issuer annotation, creates a Certificate object from the tls: block, runs the ACME flow, and lands the key pair in shop-tls — controllers all the way down. One caveat: the Ingress API is feature-frozen and ingress-nginx was retired in early 2026 — on new clusters reach for the Gateway API (Gateway + HTTPRoute) or a maintained class (Cilium, Traefik, cloud-managed); the pattern is identical.

the pattern to steal

Route traffic with replicated configuration, not with a box in the middle: publish the mapping from virtual name to live backends as data in a shared store, and let every host watch it and compile it into local forwarding rules. The data path gains no hop and no new failure point, and hosts converge on new routes without ever talking to each other.

12 persistence as intent

Storage: a claim, not a disk

Everything the control plane has managed so far is disposable. A pod dies, the ReplicaSet stamps out an identical replacement, and nothing is lost — because nothing was kept. A database breaks that assumption: its data must outlive any pod, any node, and ideally the app team's knowledge of which cloud it runs on.

Kubernetes answers with the split it uses everywhere: separate the request from the thing. The app team writes a PersistentVolumeClaim — "10Gi, class fast" — and never names a disk. In the figure, watch which cards are still lit after the pod is gone: that is the durable half of the system.

A PersistentVolumeClaim is desired state: a size and a storageClassName, written by the app team. A PersistentVolume is the record of an actual disk, cloud volume ID included. Binding matches them — the same intent/observation split as spec and status, stretched across two objects. The StorageClass names an external provisioner, and that CSI controller is another reconcile loop, running out-of-tree: watch for unbound claims, call the cloud API, post a PersistentVolume back to the ledger.

CSI is storage's CRI: a gRPC contract — CreateVolume, ControllerPublishVolume to attach a disk to a node, NodeStageVolume and NodePublishVolume to mount it — onto the node once, then into each pod. Before CSI, vendor drivers lived in the Kubernetes tree, so a cloud SDK bug shipped inside core and waited for the next Kubernetes release to fix; the contract lets vendors patch on their own schedule. One problem remains: a disk provisioned before scheduling can land in a zone the pod never reaches. volumeBindingMode: WaitForFirstConsumer defers provisioning until the scheduler places the pod, so the disk is created where the pod runs — scheduler and storage negotiating through the ledger, never calling each other.

Delete the pod and the mount is released, but the claim, the volume, and the data stay — the claim is the durable object, and pods are temporary attachments to it. Deleting the claim is the real decision point: reclaimPolicy decides whether the underlying disk is destroyed (Delete) or kept — PersistentVolume and data intact — for manual recovery (Retain). StatefulSets close the loop for replicated databases: each pod gets a stable ordinal name — pg-0, pg-1 — and a claim template keyed to that name, so a replacement pg-1 re-finds pg-1's claim instead of an empty disk.

the usual wrong model

Storage belongs to the pod: mounting a volume ties the disk's lifetime to the container, so deleting the pod deletes the data — which is why databases don't belong on Kubernetes.

what actually happens

The pod mounts a claim, not a disk, and the claim's lifetime is independent of every pod that uses it. Data is at risk only when the claim itself is deleted, and even then reclaimPolicy decides whether the underlying volume survives.

in practicestatefulset storage — each replica its own claim
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: fast
provisioner: ebs.csi.aws.com       # a CSI driver — storage's CRI
parameters:
  type: gp3
volumeBindingMode: WaitForFirstConsumer   # provision where the pod lands
allowVolumeExpansion: true         # else the 10Gi is forever
reclaimPolicy: Retain             # database class: deletion keeps the disk
---
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: pg
  namespace: shop
spec:
  serviceName: pg                  # headless Service providing pg-0.pg, pg-1.pg
  replicas: 2
  selector:
    matchLabels: { app: pg }
  template:
    metadata:
      labels: { app: pg }
    spec:
      containers:
      - name: postgres
        image: postgres:16
        env:
        - name: PGDATA             # one level below the mount — a fresh ext4
          value: /var/lib/postgresql/data/pgdata   # volume has lost+found at its root
        volumeMounts:
        - name: data
          mountPath: /var/lib/postgresql/data
  volumeClaimTemplates:            # one claim PER REPLICA: data-pg-0, data-pg-1
  - metadata:
      name: data
    spec:
      accessModes: [ReadWriteOnce] # one node at a time (ReadWriteOncePod: one pod)
      storageClassName: fast
      resources:
        requests:
          storage: 10Gi

volumeClaimTemplates mint one claim per replica (data-pg-0, data-pg-1) so identity survives rescheduling — a single shared RWO claim would deadlock the second replica. WaitForFirstConsumer lets the scheduler pick the node first so the disk is born in the right zone. And Retain means deleting the claim — or the whole namespace — leaves the disk recoverable instead of gone.

the pattern to steal

Split resource acquisition into two records — a request stating requirements and a record of the thing actually built — and let a pluggable fulfiller match them asynchronously by watching for unmet requests. The request is the durable handle: consumers die and get replaced without losing the resource, and providers ship behind a fixed RPC contract on their own release cycle.

13 nothing is privileged

Teach the ledger a new noun

Every mechanism in this deep dive — the watch streams, the reconcile loops, the ownerReferences, the leases — has been serving Kubernetes' own types. So here is the question the whole architecture has been building toward: what does it take for the ledger to hold a noun Kubernetes has never heard of, like PostgresCluster?

In most platforms the answer is fork the core or bolt a second API alongside it, and the fork is where extensions go to rot. Watch for three things: a new type arriving as plain data, its endpoint live before anything restarts, and an ordinary pod running the same loop the built-ins run — handling a database failover with nobody paged.

A CustomResourceDefinition is itself an object you POST to the API server: the schema for a new type, expressed as data. Because the request pipeline contains no per-type logic — section 03's payoff — the server starts serving the type immediately: REST endpoints under /apis/db.acme.io/v1/postgresclusters, storage in etcd, RBAC verbs, watch streams, kubectl support, even the spec/status split once the CRD opts into the status subresource — with zero changes to Kubernetes code and no restart. The failure mode this kills is the fork: a core recompiled per type turns every extension into a patch you carry forever.

An operator is that CRD plus a controller you write, running the same informer, workqueue, and reconcile loop as the built-ins — controller-runtime and kubebuilder package client-go's machinery so you write little beyond the reconcile function. Your controller ships as an ordinary Deployment: a client like every other, entering through the same door, bound by the same RBAC. Seeing a PostgresCluster, it creates the StatefulSet, Services, and Secrets with ownerReferences pointing back, so deleting the parent lets garbage collection sweep the children. The point is to encode operational knowledge — provisioning, backup, upgrade, failover — as a loop over a domain object: when the primary dies, the reconciler promotes the replica, repoints the Service, and writes status, instead of a human working a runbook at 3am.

One honest caveat: an operator is software you now maintain, and a careless loop can fight the built-in controllers over the same children — so idempotency and level-triggered discipline matter more, not less. The meta-pattern is the capstone: the extension mechanism is the core mechanism. The Deployment controller uses no API your controller cannot; nothing the built-ins rely on is privileged, and that is the strongest evidence for the design — its authors chose to live inside it.

the usual wrong model

Extending Kubernetes with a new resource type means writing a plugin the API server loads, or patching and redeploying the server — surely the server must contain code that understands each type it serves.

what actually happens

A CRD is one object you POST: a schema, stored as data, that the generic machinery serves immediately with no new server code. All behavior lives in your controller — an ordinary client pod with no special access.

in practicecrd.yaml — a new noun
apiVersion: apiextensions.k8s.io/v1
kind: CustomResourceDefinition

  name: postgresclusters.db.acme.io
spec:
  group: db.acme.io
  scope: Namespaced
  names:
    kind: PostgresCluster
    plural: postgresclusters
    shortNames: [pg]               # kubectl get pg
  versions:
  - name: v1
    served: true
    storage: true
    schema:
      openAPIV3Schema:             # validation at the door, like any built-in
        type: object
        properties:
          spec:
            type: object
            properties:
              replicas: { type: integer, minimum: 1 }
              version:  { type: string }
          status:
            type: object
            properties:
              phase: { type: string }
    subresources:
      status: {}                   # the spec/status split — for YOUR type, free
---
# apply the CRD first, then:
#   kubectl wait --for=condition=Established crd/postgresclusters.db.acme.io

  name: pg-main
  namespace: shop

Apply the CRD, wait for it to report Established (a second or two — applying CRD and instance in one shot is a classic race), and kubectl get pg, RBAC and watch streams all work. Because the status subresource is on, your controller's Role needs both postgresclusters and postgresclusters/status. The only code you write is the controller.

the pattern to steal

Build the core as a generic engine with no per-type logic, let new types register as data, and implement your own first-party features through the exact public machinery third parties use. The moment built-in code gets a private path, extensions become second-class and your public API stops being tested by the people who own it.

14 the portable core

What to Steal

Ten sections of mechanics are behind you; one question remains — what generalizes? Newcomers assume these patterns are inseparable from Kubernetes. Each is a storage-and-loop design decision that predates and outlives it: you can build a billing reconciler, a sync engine, or a provisioning system on all of them without running a single container.

The figure strips the nouns away and reruns the system as a ledger and its janitors. Watch what never has to happen: no loop hands work to another by calling it, no crash loses anything a restart cannot rebuild, and the machinery serving a brand-new row type is the machinery that served the first. The question it poses: what is the smallest set of decisions that buys all three?

"Three replicas" is safe to deliver twice, late, or out of order; "add one replica" is safe under none of those, because its meaning depends on state the sender only guessed at. So a billing reconciler stores the balance each account should be at, not charge events — duplicated or reordered events corrupt a ledger, a stated target cannot. A notification only says "look now," never carrying the work itself, which makes a missed event survivable — the fatal flaw of edge-triggered designs, where one dropped message leaves the system permanently wrong.

The bounced write is 409 Conflict rejecting a stale resourceVersion: a lock holder that dies stalls everyone behind it until a lease expires; a failed compare-and-swap costs one retry and blocks nobody. Retries stay cheap because every repair runs twice safely — create-if-absent, delete-if-present, patch-toward-target; payment systems call it idempotency keys; provisioning systems should say "ensure the VM exists," never "create the VM." The janitors read from an in-memory cache fed by a change stream, since naive polling melts the store as clients multiply; when the stream breaks, the client re-lists to heal the cache, and a periodic resync re-queues what is already cached, bounding how long a skipped reconcile can last.

Many small loops, because a central orchestrator accumulates the cross-product of every workflow's states and becomes unmodifiable. Crash-only workers — outside the store itself, no durable state — because graceful-shutdown logic is the least-tested code in most systems, and exactly the code that runs during your worst outage. The new row type is a CRD (CustomResourceDefinition), granted the same storage, versioning, watches, access control, and admission checks as built-in types; run your own platform's features through it, because the moment you keep a private, better API for yourself, the public one rots.

the usual wrong model

Newcomers assume these patterns are inseparable from Kubernetes — that you get them by adopting the platform, and that outside container orchestration they do not apply.

what actually happens

Every pattern here is a storage-and-loop design decision that predates and outlives Kubernetes. You can build a billing reconciler, a sync engine, or a provisioning system on all nine without running a single container.

the pattern to steal

When a system must keep reality matching a plan, store the plan as versioned data in one place and surround it with many small, idempotent, crash-only loops that continually converge reality toward it — coordinating through the record, never through messages between components.
